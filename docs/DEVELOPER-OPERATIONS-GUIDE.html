ShopEase PHP Lab

A practical guide for developers who need to diagnose failures, safely fix bugs, test changes, and update the deployed application without prior project knowledge.

Application: plain PHP + PDO, intentionally vulnerable security-training shop
Local database: SQLite
Hosted database: PostgreSQL/Neon when DATABASE_URL is configured
Hosting: Render Docker web service
Guide updated: 23 October 2026
Safety boundary. This application deliberately contains vulnerable behavior. Treat it as a lab, not a production shop. Keep the deployment access gate enabled, use synthetic accounts/data, and only test systems you are authorized to test. Never reset or overwrite Neon data as a troubleshooting shortcut.

Companion source: docs/DEVELOPER-OPERATIONS-GUIDE.html
Start with this guide, then check README.md for current setup and VULNERABILITIES.md for source-reviewed lab behavior.

 

1 · First response: diagnose before changing

When a page fails, first distinguish an access-gate response from an application or database failure. Do not begin by changing credentials, resetting data, or deploying a speculative fix.

What you seeLikely meaningNext safe check
ShopEase lab sign-in pageThe deployment access gate is active and the browser has not authenticated this session.Sign in with the authorized lab gate credentials. Never remove the gate to “fix” an access response.
500, PHP fatal, SQLSTATEApplication startup, route logic, or database schema/query failed.Record the exact time, route, deployment commit, and sanitized error. Check Render logs and reproduce locally.
404Wrong route, missing file, or intentionally missing resource.Verify the URL and file path/case; check whether the record exists in the active database.
Page loads but data is missingWrong database/environment, incomplete schema migration, or no matching records.Verify whether this process is using SQLite or PostgreSQL without printing secrets. Inspect schema and row counts read-only.
Browser says URL required on DeleteClient-side form validation blocked the submit before PHP received it.Check stored relative image URLs, field types, and the delete button’s formnovalidate.

Immediate checks

  1. Capture the complete error text and request path. Redact passwords, connection URLs, cookies, tokens, and flag values.
  2. Check Render deploy status and identify the exact deployed commit.
  3. Check runtime logs around the failure timestamp. Search for PHP fatal errors, SQLSTATE, startup messages, and migration/seed failures.
  4. Reproduce on a disposable local SQLite database before changing the production database.
  5. Make the smallest fix, run targeted tests and PHP lint, then review the complete diff before deployment.
  6. Exercise both states of every password visibility control, then verify normal and SQL-injection login, learner award claims, repeat submissions, distinct certificate numbers, cart, checkout (including insufficient funds), admin actions, and flag submission.
Useful rule: a successful build or a 401 from the public URL is not an authenticated smoke test. Verify deployment status separately from application behavior.

Do not expose secrets while diagnosing

Never paste DATABASE_URL, Render environment dumps, HTTP authorization headers, cookies, superadmin keys, student passwords, or database flag values into issues, logs, screenshots, or chat. Share only the error and sanitized context needed to reproduce it.

PHP warnings and errors are logged by the server and are not displayed in page responses. Diagnose them through authorized, access-controlled server logs; do not turn browser error display on to troubleshoot a deployment.

 

2 · Architecture and source map

This is a small server-rendered PHP application without a framework. Most requests load config.php, which chooses the database, initializes/updates schema, and seeds demo data. In Docker, auth_gate.php is configured as PHP’s auto_prepend_file, so the session-based access check runs before application pages and presents a branded sign-in page when needed.

PathResponsibility
config.phpVulnerability switches, session setup, database selection/connection, additive schema initialization, demo seed data, challenge-flag catalog, shared helpers.
auth_gate.phpDeployment access sign-in using LAB_AUTH_USER and LAB_AUTH_PASS, protected by a session cookie and CSRF token.
login.phpAuthentication for the seeded demo accounts and administrator-created customer accounts. Public self-registration remains disabled.
includes/password_toggle.phpShared accessible Show/Hide control for lab access, Superadmin pass-key, and learner login fields. Included by the standalone sign-in pages and shared footer.
products.php, api/search.php, product.phpStorefront, search response, product detail and cart entry.
cart.php, checkout.php, order_success.phpSession cart, order confirmation with an order-total summary and delivery form, persisted order display. Insufficient funds are checked when the learner confirms the order, not when adding an item to the cart.
admin.php, pages/Admin dashboard with store summary, product creation/editing, customer account creation/editing/deletion, order review/approval, and Hall of Heroes.
superadmin.phpSeparate pass-key-protected control panel and Hall of Heroes summary.
safe_labs.php, includes/safe_lab_simulations.phpContained simulations for every configured switch. A passed simulation can be claimed as a completion certificate; it is not proof of exploitation.
claim_award.php, submit_flag.php, generate_cert.php, includes/certificate_pdf.phpFlag and detected-login award claims, individual learner identity, unique certificate number, owned-award authorization, and dependency-free landscape PDF generation.
scripts/reset_demo_data.phpExplicit, destructive PostgreSQL demo-data reset utility. Not part of normal startup.
Dockerfile, render.yamlPHP runtime/extensions, access-gate startup, and Render environment-variable declarations.

Key data relationships

  • users, products, orders, and order_items contain shop/learner data.
  • flags holds challenge identifiers, names, and generated flag strings. Do not disclose values.
  • hall_of_fame stores submitted-flag achievements. automatic_awards separately stores detected login SQL-injection and Safe Lab simulation awards with demo-account snapshot, learner name/email, unique certificate number, achievement name, and timestamp. Safe Lab rows use distinct SAFE-LAB-* challenge identifiers and explicitly certify simulation completion only. award_claims globally reserves each challenge and case-insensitive learner email across shared demo accounts, without deleting historical award rows. Learner email addresses are not verified.
  • app_metadata stores one-time initialization markers. Do not remove markers casually; doing so can replay a seed operation.
Use VULNERABILITIES.md as an evidence-based inventory, not as proof that every VULN_* toggle has a working challenge. Preserve the lab’s explicitly intentional behaviors unless the owner asks for a security-hardening change.

 

3 · Local development and verification

Requirements

PHP 8.x with pdo_sqlite and pdo_pgsql for local SQLite and optional PostgreSQL testing. The Render image uses PHP 8.2 CLI and installs both PDO drivers. The local machine’s PHP may be newer; test with the deployed runtime when a compatibility issue is suspected.

Start an isolated SQLite copy

cd vulnapp-php
APP_DATA_DIR=/tmp/shopease-dev php -S 127.0.0.1:8081

Open http://127.0.0.1:8081. APP_DATA_DIR keeps test data away from the repository’s normal local database. Remove only the named disposable test directory when finished. Do not point local experiments at production DATABASE_URL.

When DATABASE_URL is absent, SQLite is stored at data/vulnapp.db (or under APP_DATA_DIR). On first initialization, demo users/products and the named challenge catalog are seeded if needed. Demo account details are in the project README; do not reuse them as real credentials.

Database timestamps are stored in UTC. Learner and admin award timestamps and generated certificate times are displayed in Africa/Kampala (EAT, UTC+03:00); do not change stored values to local time.

Minimum verification before a change is accepted

# From vulnapp-php/
find . -type f -name '*.php' -print0 | xargs -0 -n1 php -l
git diff --check
git status --short

Then exercise the changed flow using a clean temporary SQLite database and synthetic users. Run scripts/test_safe_lab_simulations.php and scripts/test_safe_lab_certificates.php to check every configured lab and certificate. Run scripts/test_legacy_award_schema.php for old SQLite schemas and scripts/test_postgres_award_schema.php against a disposable PostgreSQL database. For checkout, check both insufficient funds and a successful order. For admin account creation, verify validation, duplicate rejection, customer-only role, the configured password-storage mode, and a successful login; for admin edits, verify the database value and refreshed form value. For uploads, test valid and rejected files. For certificate changes, check the response with file certificate.pdf and verify the award owner check.

Operational behavior to preserve

  • Students may add low-balance items to cart; insufficient funds are reported when confirming checkout.
  • Cart quantity is at least one; checkout rechecks product and balance.
  • Search should be case-insensitive.
  • Flag upload accepts plain-text content and does not retain the uploaded file.
  • Repeated claims for the same challenge and case-insensitive learner email must reuse the original award across demo accounts; the existing certificate remains downloadable only from the account that owns it.
  • Safe Lab certificates can be claimed only after that session has passed the lab's in-memory check. The landscape PDF says “For completing” for simulations and “For discovering” for flag/detected awards; do not describe a simulation certificate as proof of a vulnerability.
  • Existing automatic_awards and award_claims tables are upgraded additively. Preserve existing rows and verify both fresh and legacy schemas.
  • Admin deletion must work even when an image field contains a relative upload path.

 

4 · Database, Neon, and flag recovery

Database selection

DATABASE_URL set to a PostgreSQL connection URL selects PostgreSQL/Neon; absent means SQLite. Keep Neon’s URL private and configured as a Render secret with SSL. Normal startup runs schema initialization and demo seed checks; it does not intentionally reset shop records.

Schema initialization adds missing columns to existing automatic_awards and award_claims tables before creating their indexes and writing awards. The migration is additive and must retain existing certificate and claim rows. Reproduce the original schema in a disposable database when investigating a save failure; never use the reset utility as a migration fix.

Never run the reset script as a generic repair. php scripts/reset_demo_data.php --confirm permanently deletes shop and learner records in the target PostgreSQL database before reseeding. It is not needed to fix a migration. Verify the target and obtain explicit approval before any destructive database operation.

Challenge flags and the required-ID incident

At startup, seed_vulnerability_flags() adds named catalog entries and records a completion marker. Existing deployments may have a legacy flags.id column without an automatic ID default; the current code calculates IDs from the existing maximum under a PostgreSQL advisory transaction lock. It should preserve legacy rows and seed only missing challenge names.

If flag seeding fails, the app logs Vulnerability flag catalog initialization failed: ... and continues initializing the shop. This is deliberate availability protection: browse/checkout routes can load, but challenge submission may fail until the catalog issue is repaired. A failure before the marker is written may be retried on each request, so inspect logs for repeated errors.

Safe recovery sequence

  1. Confirm the route error and corresponding Render log entry. Do not display flags or the Neon URL.
  2. Check the existing flags and app_metadata column definitions and current numeric IDs using a read-only, authorized database session.
  3. Back up the database before structural changes. Confirm IDs are numeric and that the unique index on vulnerability_name has no conflicting duplicate named rows.
  4. Reproduce the legacy schema in disposable SQLite/PostgreSQL test data. Confirm existing flag rows remain, new catalog names get unique IDs, and the second initialization creates no duplicates.
  5. Apply the smallest reviewed code/schema fix. Do not truncate tables, rewrite IDs referenced by achievements, drop markers, or reset demo data.
  6. After deployment, check logs and an authenticated flag-submission flow. Verify catalog count/award metadata without printing flag values.

Flag submission symptoms

  • Invalid flag: confirm the same active database contains the flag; local SQLite and Neon are separate stores. Confirm the uploaded file is plain text and within the size limit.
  • PDF not authorized/not found: the certificate route requires a signed-in learner who owns the award. Check the relevant row in automatic_awards or hall_of_fame, including its user ID and certificate number.
  • Missing student attribution: legacy awards predate identity capture. Preserve those records as legacy entries; do not invent learner names or email addresses.

 

5 · Render operation and safe deployment

Deployment boundary

The Render service name and connected repository can change; verify both in the dashboard instead of assuming they match a local folder or Git remote. The Docker command starts PHP’s built-in web server and prepends auth_gate.php. Keep these Render variables configured as secrets: LAB_AUTH_USER, LAB_AUTH_PASS, SUPERADMIN_KEY, and DATABASE_URL. The access gate shows a ShopEase sign-in page and keeps a session after successful authentication; do not remove the gate. Never place secret values in render.yaml, commits, or this guide.

Verify that Render is connected to the repository containing this PHP app and to the intended branch before expecting pushed commits to deploy. An organization may contain several repositories and services with similar names; confirm the deployed commit rather than relying on a browser tab or service label.

Release checklist

  1. Inspect git status. Stage only the files for this task; this workspace can contain unrelated changes.
  2. Run PHP lint across the app and git diff --check. Complete local, isolated smoke tests.
  3. Review the final diff, especially schema initialization, database writes, upload handlers, and admin routes.
  4. Commit with a clear message and push to the verified deployment branch.
  5. Trigger a deploy for that exact commit (or confirm auto-deploy), then wait for Render status live.
  6. Check startup/runtime logs. Confirm the public URL responds. A sign-in page only confirms the access gate is answering; use authorized credentials to exercise the protected app.
  7. Confirm a small end-to-end flow and monitor logs after the release. Report the commit and any access limitation accurately.

Render CLI examples

# Inspect latest deployments
render deploys list SERVICE_ID --output json

# Inspect recent logs (avoid sharing secrets in output)
render logs --resources SERVICE_ID --limit 100 --output json

# Deploy a reviewed, pushed commit and wait for completion
render deploys create SERVICE_ID --commit COMMIT_SHA --wait --confirm --output json

Use the actual service ID from the Render dashboard/CLI; do not assume it from an old session. Restarting is not a substitute for fixing a failing migration. Keep Neon records intact during deploys.

Rollback

If the new release causes an outage, identify the last known-good deployment in Render. Roll back to that deployment or redeploy the previous known-good commit. A code rollback does not undo database changes; keep migrations additive and backward-compatible, and handle database rollback separately with a backup and review.

A rollback, redeploy, or restart should not print or alter database credentials, reset Neon, or expose the intentionally vulnerable service by removing the access gate.

 

6 · Common problems and developer handoff

SymptomChecks and fix direction
Fatal mentions SQLSTATE 25P02PostgreSQL is reporting a command after an earlier query already aborted the transaction. The flag seeder logs the failing stage and transaction state at entry, and rolls back its transaction/savepoint. Check for the first database error and that stage in Render logs; a 25P02 alone may still be secondary.
Achievement form says it could not saveUse the reference ID shown in the error to locate the matching Award claim failed [ID] entry in Render logs. Confirm the deployed commit includes the additive automatic_awards/award_claims migration; do not infer success from the page loading or reset Neon. Reproduce against the actual legacy schema in a disposable PostgreSQL database.
Null value violates flags.idLegacy table may require explicit IDs. Use the additive catalog seeder’s max-ID logic under a transaction lock; test numeric legacy IDs and uniqueness. Do not drop the primary key/default or clear rows as a shortcut.
Shop loads, flags do notCatalog seeding is best-effort to preserve general shop availability. Inspect the catalog initialization stage and original SQLSTATE in Render logs; repair the schema/data issue before claiming flag submissions work.
Product image does not survive deployContainer-local uploads/ is not durable on Render. Use configured persistent file storage; the URL/local upload form does not itself provide persistence.
PDO driver missing locallyInstall the matching PHP SQLite/PostgreSQL PDO extension in the developer environment. The Docker image installs pdo_sqlite and pdo_pgsql.
Admin add/edit triggers header warningAdmin modules are included after the page header is emitted. Do not call header() from the included module at that stage; render a success state or move redirect handling before output.
Delete asks for an image URLCheck HTML form association and browser validation. Keep the delete button’s formnovalidate and accept relative stored upload paths in the image field.

Before handing the change to another developer

  • State the user-visible symptom, exact failing route, and the minimal steps to reproduce.
  • Provide the commit SHA, deployment status, tests run, and whether the verification used SQLite or Neon.
  • Summarize any schema change, whether it is additive, and how existing rows are preserved.
  • Include the award error reference and its sanitized Render log entry; remove secrets, cookies, learner emails/names, and challenge flag strings.
  • List unresolved checks plainly. Do not say “fixed” if only a build or unauthenticated 401 check passed.
Intentional lab vulnerabilities. Do not “clean up” vulnerable handlers or disable challenge switches as part of an unrelated bug fix. Conversely, do not expose this lab publicly without the access gate. Security hardening should be a separately scoped, owner-approved change.
